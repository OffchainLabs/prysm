# VRF tree

This package builds the VRF tree of a leanXMSS validator, and opens its leaves.

## What the spec requires

XMSS signatures are not unique, so they cannot serve as a RANDAO reveal or a
selection proof: a validator could grind them. Instead, each validator registers
the root of a Merkle tree of secret values, one for each slot, as its VRF root.

| Item         | Spec                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| Depth        | `VRF_TREE_DEPTH = 31`: 2^31 leaves, leaf `i` for slot `i`              |
| Node         | 32 bytes, `sha256(left \|\| right)`                                    |
| Root         | the VRF root, last 32 bytes of the EIP-8483 `pq_data`, or of a deposit |
| `VRFProof`   | `Vector[Bytes32, 32]`: the leaf of the slot, then its 31-node branch   |
| Verification | `is_valid_vrf_proof`, which is `is_valid_merkle_branch`                |
| Uses         | RANDAO reveal when proposing, selection proof when aggregating         |

`is_aggregator` only reads `proof[0]`, the leaf.

The spec only says that the leaves are "secret random values". Everything else
in this document is a choice of this package.

## Leaves

The leaves are derived from the validator's XMSS seed, so the XMSS seed stays
the only secret of a validator:

```text
vrf_seed = sha256(xmss_seed || "VRF_SEED")
leaf(i)  = sha256(vrf_seed || uint_to_bytes32(i))
```

`"VRF_SEED"` separates the VRF secrets from any other secret derived from the
XMSS seed. A leaf is a single 64-byte SHA-256 hash, so `Leaf(slot)` is cheap and
needs no tree.

> **Open question for the spec.** The spec defines neither this derivation nor a
> keystore format carrying a VRF secret. If two tools derive the leaves
> differently, a key generated by one cannot be used by the other: the VRF root
> it registered does not match the tree the other rebuilds. A PQ counterpart of
> EIP-2333 and EIP-2335 should settle it.

## Storage

The whole tree has `2^32 - 1` nodes of 32 bytes: 128 GiB. It cannot be stored.
Recomputing it for each proof takes tens of seconds. This package sits in
between: it caches the upper levels of the tree, and recomputes the lower ones.

```text
                   root                    ┐
                 /      \                  │ cached upper levels: height 13
             ...          ...              │ 2^14 - 1 nodes, 512 KiB
   r_0   r_1   r_2   ...   r_8191          ┘ <- subtree roots, 256 KiB
   / \   / \   / \          / \            ┐
   ...   ...   ...          ...            │ 2^13 subtrees of height 18
   leaves [k * 2^18, (k + 1) * 2^18)       ┘ recomputed to open a leaf
```

- `New` hashes every leaf once, keeps the subtree roots, and hashes the upper
  levels over them.
- `Proof(slot)` recomputes the subtree of `slot`, takes the lower 18 nodes of
  the branch from it, and the upper 13 from the cache.
- `Leaf(slot)` hashes the leaf only.

### Subtree height

`subtreeHeight` trades the memory of the cache against the time to open a leaf.
Measured on an Apple M2 Max:

| `subtreeHeight` | Cache in memory | Subtree roots | `Proof`  | Allocated by `Proof` |
| --------------- | --------------- | ------------- | -------- | -------------------- |
| 16              | 2 MiB           | 1 MiB         | ~7 ms    | 8 MiB                |
| **18**          | **512 KiB**     | **256 KiB**   | ~27 ms   | 32 MiB               |
| 20              | 128 KiB         | 64 KiB        | ~114 ms  | 128 MiB              |

A validator needs a full proof only when it proposes, or when it is selected as
an aggregator, and it knows its duties an epoch ahead. 18 keeps a proof well
within a slot, with a small cache.

## Costs

With `subtreeHeight = 18`, measured on an Apple M2 Max (12 cores):

| Operation                         | Per key          | 1,000 keys        |
| --------------------------------- | ---------------- | ----------------- |
| `New`: 2^32 - 1 hashes, all cores | ~21 s            | ~6 h              |
| `FromSubtreeRoots`                | ~0.5 ms          | ~0.5 s            |
| `Proof`: ~2^19 hashes, one core   | ~27 ms           |                   |
| `Leaf`: 1 hash                    | negligible       |                   |
| Cache in memory                   | 512 KiB - 32 B   | ~500 MiB          |
| Subtree roots on disk             | 256 KiB          | ~250 MiB          |

Hashing goes through `htr.Hash`, so it follows the `hashtree` feature flag. On
arm64, both libraries take the same time.

## Saving the tree

`New` is too slow to run for every key at every start. Instead:

- `SubtreeRoots` returns the 2^13 subtree roots to save, 256 KiB per key.
- `FromSubtreeRoots` rebuilds the tree from them and the XMSS seed, hashing the
  upper levels only. It refuses them if the root of the tree is not the expected
  VRF root, so a wrong, truncated or swapped file is detected.

This package does not read or write files. Saving and loading the roots belongs
to key loading, which is not implemented yet. The intended behavior:

- Build the tree when a key is imported, and save its subtree roots, for
  instance in `<datadir>/validator-client-data/vrf-trees/0x<xmss pubkey>`.
- At startup, rebuild the tree from the saved roots. If they are missing or
  refused, rebuild the tree in the background: until it is ready, the key still
  attests and checks `is_aggregator` with `Leaf`, and only its proposals and
  aggregations fail.
- When importing through the keymanager API, build the tree in the background,
  since the request cannot wait tens of seconds per key.

The subtree roots are not secret: they are hashes of the secret leaves, and
proofs reveal upper nodes on chain anyway. They need no encryption. Losing them
costs one rebuild, unlike the signing protection data, which must never be lost.

## Safety

- **Invalid proof.** `Proof` checks its branch against the root of the tree
  with `is_valid_merkle_branch` before returning it, for 31 hashes. It never
  returns a proof the chain would refuse, even if the cache is corrupted in
  memory.
- **Wrong saved roots.** `FromSubtreeRoots` checks the root against the expected
  VRF root.
- **Leaf beyond the tree.** `Leaf` and `Proof` refuse a slot from 2^31 on.
- **Slow build.** `New` takes a context, and stops within about one subtree when
  it is canceled.

## Tests

The tests use a tree of depth 8 and check the package against a naive
implementation, which hashes the whole tree level by level, and against the
spec's `is_valid_merkle_branch`:

- every subtree height from 1 to 8 gives the same root;
- the proof of every slot is valid, and the leaf of every slot is the first
  element of its proof;
- a tree rebuilt from its subtree roots gives the same proofs;
- corrupted, missing or mismatching subtree roots are refused;
- a corrupted cached node makes the proofs through it fail, and only those.
