# VRF tree

This package builds the VRF tree of a leanXMSS validator, and opens its leaves.

## What the spec requires

XMSS signatures are not unique. They cannot serve as a RANDAO reveal or a
selection proof: a validator could grind them. Instead, each validator registers
the root of a Merkle tree as its VRF root. The leaf of a slot commits to a secret
value of the validator for this slot.

| Item         | Spec                                                                   |
| ------------ | ---------------------------------------------------------------------- |
| Depth        | `VRF_TREE_DEPTH = 31`: 2^31 leaves, leaf `i` for slot `i`              |
| Node         | 32 bytes, `keccak256(left \|\| right)`                                 |
| Root         | the VRF root, last 32 bytes of the EIP-8483 `pq_data`, or of a deposit |
| `VRFProof`   | `Vector[Bytes32, 32]`: the secret of the slot, then its 31-node branch |
| Leaf         | `compute_vrf_leaf`: `keccak256("VRF_LEAF" \|\| secret \|\| slot)`      |
| Verification | `is_valid_vrf_proof`, a Merkle branch check with Keccak-256            |
| Uses         | RANDAO reveal when proposing, selection proof when aggregating         |

The RANDAO mix only reads `proof[0]`, the secret.

Everything else
in this document follows the ethPandaOps genesis tool and Lighthouse
(`beacon_node/genesis/src/pq.rs` of the `pq-devnet-0` branch).

## Leaves

The validator client derives the first 2^20 leaves from its BLS secret key:

```text
sk       = the 32-byte BLS secret key of the validator, at m/12381/3600/<index>/0/0
vrf_seed  = sha256("vrf-seed" || sk)
secret(i) = keccak256("VRF_SECRET" || vrf_seed || uint64_le(i))    for i < 2^20
leaf(i)   = keccak256("VRF_LEAF" || secret(i) || uint64_le(i))
```

`Secret(slot)` is a single Keccak-256 hash, and needs no tree.

The leaves from 2^20 on are not derived by the validator client. The tree is
then one of:

- **Padded** (`New`): every leaf from 2^20 on is zero. A zero leaf commits to no
  secret, so these slots have no proof.
- **Full** (`NewFull`): the leaves from 2^20 on are only known to the genesis
  tool. The VRF root the devnet registers is the root of this tree. The tool
  publishes the VRF state: for each validator, its VRF root and the branch of
  the leaf of slot 0. The 11 upper nodes of this branch join the derived part
  to the root. `NewFull` checks that they are not roots of zero subtrees, that
  the derived part and these nodes hash to the root, and that the lower 20
  nodes of the branch match the derived leaves. A full tree opens the slots
  below 2^20 only. This is the tree of Lighthouse's
  `VrfTree::from_slot_zero_state`.

> **Open question for the spec.** The spec defines neither this derivation nor
> a keystore format carrying a VRF secret. If two tools derive the leaves
> differently, a key generated by one cannot be used by the other: the VRF root
> it registered does not match the tree the other rebuilds.

## Storage

The derived part of the tree has `2^21 - 1` nodes of 32 bytes: 64 MiB per key.
This package caches the upper levels of the derived part only, and recomputes
the lower ones.

```text
                   root                    ┐ levels 20 to 31: the root of the derived
                  /    \                   │ part, hashed with 11 siblings: zero subtrees
               ...      sibling            │ (padded) or published nodes (full)
                 r                         ┘
             /       \                     ┐ levels 14 to 20: 127 nodes
   r_0   r_1   ...   r_63                  ┘ <- roots of the derived subtrees
   / \   / \          / \                  ┐
   ...   ...          ...                  │ 64 subtrees of height 14
   leaves [k * 2^14, (k + 1) * 2^14)       ┘ recomputed to open a leaf
```

- `New` and `NewFull` hash every derived leaf once, keep the subtree roots, and
  hash the upper levels over them.
- `Proof(slot)` recomputes the subtree of `slot`, takes the lower 14 nodes of
  the branch from it, the next 6 from the cache, and the upper 11 from the
  siblings. In a padded tree, the branch of a slot from 2^20 on comes from the
  zero subtrees and the nodes of index 0 of the upper levels.
- `Leaf(slot)` hashes the leaf only.

## Costs

With `subtreeHeight = 14`, measured on an Apple M2 Max (12 cores):

| Operation                                | Per key    | 1,000 keys |
| ---------------------------------------- | ---------- | ---------- |
| `New`/`NewFull`: ~2^21 hashes, all cores | ~140 ms    | ~2.5 min   |
| `Proof`: ~2^15 hashes, one core          | ~13 ms     |            |
| `Leaf`: 1 hash                           | negligible |            |
| Cache in memory                          | ~4.5 KiB   | ~4.5 MiB   |

## Safety

- **Invalid proof.** `Proof` checks its branch against the root of the tree
  before returning it, for 31 hashes. It never returns a proof the chain would
  refuse, even if the cache is corrupted in memory.
- **Leaf beyond the tree.** `Leaf` and `Proof` refuse a slot from 2^31 on, and
  from 2^20 on in a full tree.
- **Wrong VRF state.** `NewFull` refuses a root or a branch that does not match
  the derived leaves.
- **Slow build.** `New` and `NewFull` take a context, and stop within about one
  subtree when it is canceled.

## Tests

- The root of the padded tree and the proofs of slots 0, 5, 2^20 - 1, 2^20 and
  2^31 - 1 match the test vector of Lighthouse.
- The full tree built from Lighthouse's published VRF state of validator 5 of
  the ethPandaOps devnet mnemonic (`testdata/full-vrf-state.index-5.bin`) has
  the published root, and opens slots 0, 5 and 2^20 - 1. A corrupted branch or
  root is refused.
- The other tests use a tree of depth 8 and check the package against a naive
  implementation, which hashes the whole tree level by level, and against
  `is_valid_vrf_proof`:
  - every populated depth and subtree height give the same root;
  - the proof of every slot is valid, and the leaf of every slot is the first
    element of its proof, in padded and full trees;
  - a corrupted cached node makes the proofs through it fail, and only those.
