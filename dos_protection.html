Bundled attestation propagation · threat analysis

What damage can an attacker do?

Peers exchange attestations keyed by their attestation_data. That data is free to fabricate — every field tweak mints a fresh identity, and fabricating it is not slashable. Whether a given data is real is decidable only against chain state, and sometimes not decidable yet: it may name a block that is honestly a few seconds behind. This page walks the attacks abstractly, independent of any implementation.

Attack · random attestation data spam

Spam us with messages carrying fabricated attestation data

The attacker sends well-formed messages whose attestation_data is random. Structurally they are indistinguishable from honest traffic. Two distinct harms follow.

Harm 1 · slot theft

Junk crowds out data we cannot judge yet

Every admission structure is finite: queue positions, cache entries, tracked keys — call them slots. The dangerous collision is not junk against validated data (validated data is already proven and easy to protect). It is junk against honest-but-undecidable data: an attestation naming a block we have not seen only because of ordinary propagation delay. At arrival the two are indistinguishable, and if junk may hold slots, the honest racer loses its place.

Anything provably bad is rejected before a slot is allocated; what remains undecidable — including junk we cannot expose yet — is admitted only into a pool that is small, short-lived, and bounded per peer, so it can never squeeze honest traffic out.

The lever is the verdict system. Two verdicts (valid / invalid) are not enough — the whole attack lives in the gap between them:

Accept proven

Fully validated. Protected by its own proof — never competes for slots again.

Reject proven bad

Provably inconsistent with the chain. Never occupies a slot, and the proof implicates the direct sender — this is the punishable verdict.

Undecidable wait

Names a root we do not hold — indistinguishable from junk at arrival, no test exists. The only thing slots are for. Must stay retryable, must never be punished — honest peers race block propagation constantly.

But how do we know the data is junk?

For the decisive case, we don’t — no test exists. Split by what the data names:

— a block we hold: every other field is now pinned — the checkpoints it names must be that block’s ancestors in our in-memory view of the chain. Any mismatch is provably bad, cheaply.
— an out-of-window slot: worthless whether or not it is real. Free discard.
— a root we do not hold: indistinguishable from the root of a real block that is two seconds behind. This is the attacker’s best move, and it lands in the same bucket as the honest race.

So for unknown roots the defense cannot be detection — it must be economics. Junk is never exposed, it is outlived: an honest race resolves within seconds when its block arrives and the data moves to the provable buckets; junk never resolves, and its slot simply expires. Three properties make this safe to run cheaply:

1. Expiry replaces detection. Undecidable slots carry a short lifetime; past it, the data either became judgeable or stopped mattering.
2. The hold is necessary, not optional. The network does not re-offer: senders forward an attestation once and mark us covered, and validated copies stop being advertised or servable within seconds. A racer that outlives its in-flight duplicates is recoverable only from our own hold — so the pool must exist, and its bounds (short lifetime, per-peer caps) are what keep it from becoming the attack surface of harm 1.
3. Never punish, never work. No penalty for undecidables (that would grief honest racers), and no expensive work on their behalf — an unknown root must not trigger unbounded fetching.

But the hold is finite — can’t the attacker just fill it?

Yes — holding the undecidable only relocates the slot theft into the pending pool, which is exactly harm 1 again. And losing an honest racer is not cheap: a dropped unaggregated attestation is a missed vote — the attester’s reward and its participation weight, gone. So we cannot argue the harm away; the goal is to never evict an honest racer in the first place. A shared buffer with global eviction fails that. A hard per-peer allowance achieves it structurally.

The slot unit is one distinct unknown attestation_data, not one signature: a bundle with many positions under one unknown data occupies a single slot, so a peer’s entire pending footprint is at most 2–3 entries no matter how much it packs.

An attacker on one identity can only ever fill its own 2–3 slots and cannot touch any other peer’s — so a spammer never causes an honest racer to be dropped. There is no cross-peer contention to reason about. Spam collapses into Sybil (many identities for volume), governed by connection admission — the same endgame as every other branch here.

Why 2–3 is enough: a peer holds an undecidable only while it has seen a block we have not — a brief, narrow condition — so an honest peer’s working set of racing data is one or two at a time, and a short lifetime recycles the slots as races resolve.

Harm 2 · forced disk access

Cheap messages that buy expensive work

Validation cost is tiered: structural checks are free; consistency against in-memory chain knowledge is cheap; resolving historical state can mean disk reads or replaying state — seconds of work; signature checks cost real CPU. The attack is asymmetry: if any attacker-chosen field can select disk-tier work before the data is pinned to the chain, one small message buys seconds of our time, repeatable forever.

“Pin to chain” means: every attacker-chosen field is checked against what we already hold in memory — the named block must be known, and the named checkpoints must be its ancestors — before any state resolution. Data that passes can only name the canonical chain, where state lookups are cache hits. The expensive tier becomes unreachable with attacker-chosen values.

Ordering is the whole defense. Each tier may only be entered by messages the previous tier could not condemn, and the expensive tiers must be reachable only by data already proven to live on our chain. A useful invariant to state in the spec: no attacker-chosen value selects disk work.

Stress test · a long fork resolves

Fork length is irrelevant here — it lands on block sync

The worst case for “hold the undecidable” sounds like a long fork resolving: suddenly a whole competing chain to reconcile. But almost none of that reaches attestation propagation. Slots are wall-clock, so a validity window of the current plus previous epoch admits at most ~2 epochs of attestations no matter how long the fork ran. Everything older is rejected for free and arrives instead as votes already baked into the blocks we sync.

The old slots (red) never enter attestation propagation; only the in-window tail (amber) does. Fork length is absorbed entirely by the block/state path — download, replay, reorg — which was never this component’s duty.

And the in-window burst has exactly the shape the per-peer allowance handles: many peers pointing at the same few winning-fork heads, not one peer inventing many data. Each honest peer holds one or two undecidable heads — inside 2–3 with margin. As the fork’s blocks arrive, that data crosses from undecidable to proven and drains naturally; junk checkpoints still match nothing and still reject. The stress test mostly just confirms the three choices already made: the window bound, the per-peer hold, and not fetching on an undecidable’s word.

One honest tension the fork exposes: “many validators vote for a head I have never seen” is also how a node legitimately discovers a missed head and goes to fetch it. That self-healing hint and the fetch-amplifier attack are the same mechanism — which is why letting block sync drive discovery, and never fetching on an unproven root, is a deliberate tradeoff rather than a free win.

Synthesis

One rule covers both harms

Classify every message as early as possible into provably bad / undecidable / proven, using only checks cheaper than what the next tier would spend. Then:

— spend slots only on the undecidable,
— spend disk only on the pinned,
— spend punishment only on the provable.

Punishment closes the loop: every provable reject implicates the direct sender (honest peers forward only what they validated themselves, so there is no innocent relay), and a punished sender must return with a fresh identity. Sustained spam degenerates into identity churn, which connection admission already governs.

Everything above is independent of implementation. The concrete mapping — which checks pin the data, which structures are the slots, how punishment is delivered — lives in dos_protection.md.
